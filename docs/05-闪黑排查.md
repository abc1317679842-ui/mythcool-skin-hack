# 05 · 副屏闪黑现象：与注入器的关系、排查与最终方案

> 本项目开发期间，作者的机箱副屏出现过**不定期闪黑**：整屏黑几十到几百毫秒后画面自愈，
> 内容不丢、无需任何操作。本文记录为定位它做过的测试、处置尝试与排查方向，
> 供遇到同类现象的人参考。
>
> 先说结论：**不能完全确认本注入器没有任何影响，但它大概率不是闪黑的主因。**
> 截至本文最后更新（2026-09-30，含一次完整取证），**具体原因仍未定位**。
> 本文把查过的方向如实列出，如果有人还想继续排查，可以直接拿去当参考；
> 重装官方软件有缓解但不根治。

---

## 1. 先定性：闪黑 ≠ 断流 ≠ 坏屏

同类现象至少有三个层次，**排查前先区分**（混在一起讨论会浪费大量时间）：

| 层次 | 表现 | 通常原因 |
|---|---|---|
| **推流断流** | 黑屏期间 USB 推流实际停了；恢复慢，可能先出现 logo / 待机画面 | 驱动、USB 链路、带宽问题 |
| **渲染层闪** | 黑一下内容还在，自愈快（几十~几百 ms） | 页面渲染抖动、软件自身 |
| **屏模块故障** | 规律性黑屏、固件级异常，软件侧怎么调都没用 | 屏批次 / 硬件，需换屏 |

本文的现象属于第二层。判据：把 USB 推流日志按毫秒逐行分析（该屏推流有稳定的心跳），
**闪黑发生的时刻推流完全正常** —— 心跳间隔远小于人眼看到的黑屏时长 ⇒ USB 传输、
驱动、推流线程全部排除，问题在页面渲染层或屏本身。

> ⚠️ 分析日志的**时钟伪影陷阱**：Windows NTP 校时会把系统时间前拨/后拨几百毫秒到几秒，
> 在日志里制造出「秒级空档」的假象。判定「推流中断」之前，先查同一时刻有没有
> 时间更改事件（Kernel-General Id=1）+ 日志时间戳有没有回退。作者就差点被这个坑骗过去。

---

## 2. 与注入器的关系：A/B 对照

注入器只改渲染进程的 DOM/CSS，不碰 USB 推流通道；frida 注入完成后即与目标进程分离。
但「架构上无关」不等于「实测无关」，所以做了对照：

| 测试 | 结果 |
|---|---|
| **停用注入器**期间 | 闪黑**照样发生**（该时段恰为软件启动后不久，只能证明注入器不是必要条件） |
| **注入在岗**期间 | 仍偶发，无明显规律 |
| 卸载 Myth.Cool + 清残留 + 重装 + 重启 + 重开注入 | 开启注入状态下数小时未复现（此前每天多次）→ **当晚仍复现**（2026-09-30 02:16，见 §4） |

**结论**：不能完全确认零影响，但注入器大概率不是主因。
遇到闪黑请先做「停用注入器 10 分钟」对照，再归因。

## 3. 排查过程中排除 / 确认的事

以下均为作者环境实测，供参考（你的环境结论可能不同）：

**已实测排除：**

- **USB 选择性暂停 / 电源管理**：`powercfg` 确认 AC/DC 均已禁用后，闪黑照旧 ⇒ 不是电源挂起。
  （作为通用排查手段仍值得一试，但对本现象无效）
- **主显示器问题**：主屏全程正常，现象只出现在机箱副屏。
- **换主板内置 USB 接口**：换到另一组针脚无效（两组口往往挂在同一个 USB 控制器下，带宽池相同）。

**实测确认的软件侧嫌疑：**

- **Myth.Cool 高频自我重启**：作者环境实测每天 9~12 次，每次重启 = 黑约 2.4 秒 +
  重启前推流空窗 —— 这本身就是一个「黑一下」的来源。
- **灰度版本混用**：Myth.Cool 存在灰度更新机制，实测出现过**主程序与皮肤页面版本不一致**
  （主程序稳定版 + 页面跑灰度版代码）。判断版本时只看主程序版本号会误判。
- **厂商驱动栈老旧**：屏用厂商定制的 libusb-win32 驱动（2022~2024 年版本），业界公认不算稳定。
- **监控/灯控软件冲突**：网上有明确案例 —— Myth.Cool 与主板厂商灯控套件
  （华硕奥创 / MSI Center / Mystic Light 等）共存时随机花屏、闪屏，卸载灯控后恢复。
  多套软件抢底层硬件（USB / SMBus / 内核驱动）是通用冲突模式。

## 4. 处置尝试与当前状态（2026-09-30 更新）

### 4.1 「清洁卸载重装」：缓解，不根治

按顺序执行：

1. **卸载 Myth.Cool**（系统「应用」里正常卸载）
2. **用清理软件把残留清干净** —— 重点：AppData / ProgramData 下的残留目录、注册表残留。
   这一步最关键：实测发现卸载后**皮肤页面仍可能跑旧版本（灰度）代码**
3. 从官网**重新下载安装**最新版
4. **重启电脑**
5. 重新开启皮肤注入

结果（如实记录，两次修正）：

- 做完后此前每天多次的闪黑，**数小时未复现** —— 当时以为大概率好了
- **2026-09-30 02:16 复现**（重装 + 注入器 v20 运行中）—— 观察期的保守判断应验了

⇒ **结论修正：重装是「缓解」（复现频率可能下降），不是根治。** 仍然值得做
（成本最低、排掉了灰度版本混用这个变量），但别指望它单独解决问题。

### 4.2 02:16 复现的取证 —— 三条线全部干净

复现后立即抓取的数据（这条证据链比之前的更完整）：

| 层 | 数据 | 结论 |
|---|---|---|
| **USB 推流** | 覆盖闪屏时刻的日志（02:11:58–02:18:10）10000 个心跳，**>100ms 空档 = 0** | 推流一帧没断 |
| **注入器** | `inject.log` 在注入成功后到闪屏时刻**零新行**——无重注入、无热调、无告警 | 注入器当时完全静默 |
| **系统层** | System 事件日志 02:05–02:19 **完全为空**（连时间更改事件都没有） | 排除时钟伪影、无任何系统级异动 |

⇒ 注入器、推流、驱动、系统层全部排除，**闪在页面渲染层或屏本身** —— 与 §1 的定性一致，
且这次是「注入器 v20 + 干净重装」状态下的复现，嫌疑面进一步收窄。

### 4.3 继续排查的方向：皮肤来源

一个此前被忽略、值得切开的变量：**皮肤本身的来源**。

- 出问题时用的是 **AeeBiCui「博物馆1」——第三方皮肤**（Myth.Cool 皮肤商店里有作者链接）
- 软件自带的「梦境」「洛音」等是**官方皮肤**

第三方皮肤完全可能带自己的动画 / 定时器 / 特效资源（这正是渲染层抖动的经典来源），
而此前所有排查都在「注入器 ↔ 软件 ↔ 硬件」之间打转，皮肤来源这个变量一直没切开。

**验证方法（零成本）**：换成官方皮肤长时间观察 ——
- 换皮后**不再闪** → 皮肤嫌疑坐实，方向转向「第三方皮肤的质量/实现」
- 换皮后**仍闪** → 皮肤嫌疑排除，回到「软件自身 / 屏」的方向

作者正在按这个方向本地验证（截至本文更新尚无结论，不预设结果）。

## 6. 遇到闪黑怎么办（给用户的排查顺序）

1. **停用注入器对照 10 分钟** —— 先排除/确认注入器（删计划任务或 `schtasks /Change /TN <任务名> /DISABLE`，对照完记得 `/ENABLE`）
2. **定性**：黑屏时内容还在吗？多久恢复？出现 logo / 待机画面吗？（§1 的三层区分）
3. **干净重装 Myth.Cool**（§4.1）—— 成本最低，实测**缓解但不根治**，仍建议先做（顺便排掉灰度版本混用变量）
4. **换官方皮肤对照**（§4.3）—— 排除/确认第三方皮肤这个变量
5. **退出主板厂商灯控/监控套件对照**（MSI Center / 奥创等）—— 通用冲突模式
6. 仍闪 → 查屏的生产日期（背面标签 / 报 SN 给客服），参考网上「换屏解决」先例找售后
