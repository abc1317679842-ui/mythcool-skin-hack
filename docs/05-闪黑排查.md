# 05 · 副屏闪黑现象：排查思路与一次未完成的定位

> 本项目开发期间，作者的机箱副屏出现过**不定期闪黑**：整屏黑几十到几百毫秒后画面自愈，
> 内容不丢、无需任何操作。本文记录为排查它做过的测试、处置尝试与**目前的进展**，
> 供遇到同类现象的人参考。
>
> ## ⚠️ 先看这里：**本文没有找出确切原因**
>
> 这一点必须写在最前面。目前确认的事实是：
>
> | | 状态 |
> |---|---|
> | **① 该皮肤最底层确实是一整层动态**（全屏铺满、持续动画） | ✅ 事实（解包可复现，§4.4.1） |
> | **② 只冻结了这一层，实测 6~7 小时暂未再发现闪黑** | ✅ 实测 |
> | **③「为什么这一层会闪」的确切原因** | ❌ **未知。本文给不出** |
>
> ### 关键区别：不是「有没有动态」，而是「**哪一层**」是动态
>
> 这一点很容易被说错，先澄清：
>
> - **官方皮肤也有动态** —— 它们带**粒子特效**等上层动画，有些也在动；
> - 但它们的**最底层不是全屏动态层**；
> - AeeBiCui 的**最底层是一整层铺满全屏的持续动态**。
>
> 所以本次测试的观察是：**只把「最底层那层全屏动态」禁掉，上层那些动态组件（粒子、
> GIF、轮播、数字）全都还在动**，而闪黑暂时不再出现。
> **这在指向「是这层的位置/层级特殊」，而不是「有东西在动就会闪」。**
>
> ### 本次冻结的实际范围（别说成「全部冻住了」）
>
> | 层 | 状态 |
> |---|---|
> | **最底层全屏动态** | **已禁用** ← 本次唯一动的地方 |
> | 上层组件（GIF 小人、粒子、轮播、数字刷新） | **仍全部在动，没禁** |
>
> 准确说法是：**「只禁掉最底层那层全屏动态，上层动态组件照动」** ——
> 不是「把整个皮肤冻成静态」。
>
> ### 剩下能说的：几种**可能**（都未验证）
>
> 见 §4.6，列了几条可能性。但请注意：**这些都是推测，作者没有去抓底层证据，
> 也不打算再花时间继续解析了。** 本节止步于此。
>
> ### 诚实边界
>
> - 观察期只有 **6~7 小时**，不是几天/几周的长周期验证；
> - 皮肤是**因人而异**的 —— 你未必装了这个皮肤，装的同名皮肤也可能来自不同版本；
> - **不能替别人的机器下结论**，本文给的是一套**排查思路**，不是药方。
>
> 另外：**注入器本身不碰 USB 推流通道**（只改渲染进程的 DOM/CSS），
> 闪黑与「注入器是否在岗」看不出因果关系 —— 详见 §2。

## 1. 先定性：闪黑 ≠ 断流 ≠ 坏屏

同类现象至少有三个层次，**排查前先区分**（混在一起讨论会浪费大量时间）：

| 层次 | 表现 | 通常原因 |
|---|---|---|
| **推流断流** | 黑屏期间 USB 推流实际停了；恢复慢，可能先出现 logo / 待机画面 | 驱动、USB 链路、带宽问题 |
| **渲染层闪** | 黑一下内容还在，自愈快（几十~几百 ms） | 页面渲染抖动、软件自身 |
| **屏模块故障** | 规律性黑屏、固件级异常，软件侧怎么调都没用 | 屏批次 / 硬件，需换屏 |

本文的现象属于第二层。判据：把 USB 推流日志按毫秒逐行分析（该屏推流有稳定的心跳），
**闪黑发生的时刻推流完全正常** —— 心跳间隔远小于人眼看到的黑屏时长 ⇒ USB 传输、
驱动、推流线程全部排除，问题在页面渲染层或屏本身。

> ⚠️ 分析日志的**时钟伪影陷阱**：Windows NTP 校时会把系统时间前拨/后拨几百毫秒到几秒，
> 在日志里制造出「秒级空档」的假象。判定「推流中断」之前，先查同一时刻有没有
> 时间更改事件（Kernel-General Id=1）+ 日志时间戳有没有回退。作者就差点被这个坑骗过去。

---

## 2. 与注入器的关系：A/B 对照

注入器只改渲染进程的 DOM/CSS，不碰 USB 推流通道；frida 注入完成后即与目标进程分离。
但「架构上无关」不等于「实测无关」，所以做了对照：

| 测试 | 结果 |
|---|---|
| **停用注入器**期间 | 闪黑**照样发生**（该时段恰为软件启动后不久，只能证明注入器不是必要条件） |
| **注入在岗**期间 | 仍偶发，无明显规律 |
| 卸载 Myth.Cool + 清残留 + 重装 + 重启 + 重开注入 | 开启注入状态下数小时未复现（此前每天多次）→ **当晚仍复现**（2026-09-30 02:16，见 §4） |

**结论**：不能完全确认零影响，但注入器大概率不是主因。
遇到闪黑请先做「停用注入器 10 分钟」对照，再归因。

## 3. 排查过程中排除 / 确认的事

以下均为作者环境实测，供参考（你的环境结论可能不同）：

**已实测排除：**

- **USB 选择性暂停 / 电源管理**：`powercfg` 确认 AC/DC 均已禁用后，闪黑照旧 ⇒ 不是电源挂起。
  （作为通用排查手段仍值得一试，但对本现象无效）
- **主显示器问题**：主屏全程正常，现象只出现在机箱副屏。
- **换主板内置 USB 接口**：换到另一组针脚无效（两组口往往挂在同一个 USB 控制器下，带宽池相同）。

**实测确认的软件侧嫌疑：**

- **Myth.Cool 高频自我重启**：作者环境实测每天 9~12 次，每次重启 = 黑约 2.4 秒 +
  重启前推流空窗 —— 这本身就是一个「黑一下」的来源。
- **灰度版本混用**：Myth.Cool 存在灰度更新机制，实测出现过**主程序与皮肤页面版本不一致**
  （主程序稳定版 + 页面跑灰度版代码）。判断版本时只看主程序版本号会误判。
- **厂商驱动栈老旧**：屏用厂商定制的 libusb-win32 驱动（2022~2024 年版本），业界公认不算稳定。
- **监控/灯控软件冲突**：网上有明确案例 —— Myth.Cool 与主板厂商灯控套件
  （华硕奥创 / MSI Center / Mystic Light 等）共存时随机花屏、闪屏，卸载灯控后恢复。
  多套软件抢底层硬件（USB / SMBus / 内核驱动）是通用冲突模式。

## 4. 处置尝试与当前状态（2026-09-30 更新）

### 4.1 「清洁卸载重装」：缓解，不根治

按顺序执行：

1. **卸载 Myth.Cool**（系统「应用」里正常卸载）
2. **用清理软件把残留清干净** —— 重点：AppData / ProgramData 下的残留目录、注册表残留。
   这一步最关键：实测发现卸载后**皮肤页面仍可能跑旧版本（灰度）代码**
3. 从官网**重新下载安装**最新版
4. **重启电脑**
5. 重新开启皮肤注入

结果（如实记录，两次修正）：

- 做完后此前每天多次的闪黑，**数小时未复现** —— 当时以为大概率好了
- **2026-09-30 02:16 复现**（重装 + 注入器 v20 运行中）—— 观察期的保守判断应验了

⇒ **结论修正：重装是「缓解」（复现频率可能下降），不是根治。** 仍然值得做
（成本最低、排掉了灰度版本混用这个变量），但别指望它单独解决问题。

### 4.2 02:16 复现的取证 —— 三条线全部干净

复现后立即抓取的数据（这条证据链比之前的更完整）：

| 层 | 数据 | 结论 |
|---|---|---|
| **USB 推流** | 覆盖闪屏时刻的日志（02:11:58–02:18:10）10000 个心跳，**>100ms 空档 = 0** | 推流一帧没断 |
| **注入器** | `inject.log` 在注入成功后到闪屏时刻**零新行**——无重注入、无热调、无告警 | 注入器当时完全静默 |
| **系统层** | System 事件日志 02:05–02:19 **完全为空**（连时间更改事件都没有） | 排除时钟伪影、无任何系统级异动 |

⇒ 注入器、推流、驱动、系统层全部排除，**闪在页面渲染层或屏本身** —— 与 §1 的定性一致，
且这次是「注入器 v20 + 干净重装」状态下的复现，嫌疑面进一步收窄。

### 4.3 继续排查的方向：皮肤来源

一个此前被忽略、值得切开的变量：**皮肤本身的来源**。

- 出问题时用的是 **AeeBiCui「博物馆1」——第三方皮肤**（Myth.Cool 皮肤商店里有作者链接）
- 软件自带的「梦境」「洛音」等是**官方皮肤**

第三方皮肤完全可能带自己的动画 / 定时器 / 特效资源（这正是渲染层抖动的经典来源），
而此前所有排查都在「注入器 ↔ 软件 ↔ 硬件」之间打转，皮肤来源这个变量一直没切开。

**验证方法（零成本）**：换成官方皮肤长时间观察 ——
- 换皮后**不再闪** → 皮肤嫌疑坐实，方向转向「第三方皮肤的质量/实现」
- 换皮后**仍闪** → 皮肤嫌疑排除，回到「软件自身 / 屏」的方向

作者实测结果：**换成官方自带皮肤后，几乎不再观察到闪黑** ⇒ 皮肤这个变量被坐实。
（下一步不是换皮肤了事 —— 而是继续切开「皮肤的哪一部分」。）

### 4.4 决定性线索：闪的是**哪一层**？

闪黑很快，容易看成「整屏黑」。但盯住看能分辨出**空间范围**：

> 作者原话：「我隐约感觉好像它上面的组件没有闪，**闪黑的是它最下面的那个动态**。」
>
> —— 上方静态组件（数据文字、图标、进度条）**没闪**，黑掉的只有**最底层那块
> 持续动画的区域**。

这个观察把嫌疑从「整个页面 / 整条链路」一下缩到**一个具体的渲染层**。
于是有了下一条 A/B 测试。

#### 4.4.1 拆开皮肤安装包，直接看底层是什么（**本次新增的硬证据**）

空间特征只是「看出来的」，下面这条是**从皮肤安装包里挖出来的源码级证据** ——
不需要装皮肤、不需要抓帧，任何人拿到 `.gpk` 都能自己复现。

**皮肤是打包在 `.gpk` 里的**（位于
`%LOCALAPPDATA%\MythCool\Apps\<应用id>\<版本>\dial<编号>.gpk`）。
这是一个自定义封包，格式极简、**无压缩表、无加密**：

```
[1 字节 0x00][JSON 目录][数据区：各文件按 offset 顺序平铺]
```

目录 JSON 的每个叶子节点是 `{"size": N, "zipped": 0|1, "offset": "N"}`，
`offset` 相对数据区起点。解析出来就能把所有资源原样导出。

**AeeBiCui「博物馆1」= `dial31.gpk`（5.68 MB，13 个文件）**，导出后是这样：

| 文件 | 尺寸 | 大小 | 是什么 |
|---|---|---|---|
| `fg_img_people_01.gif` | 310×480 | 1.28 MB | **GIF 动图**，50 帧，单帧 40ms |
| `fg_img_people_02.gif` | 310×480 | 1.74 MB | **GIF 动图**，50 帧，单帧 40ms |
| `fgcp_img_01.gif` | 280×220 | 1.38 MB | **GIF 动图**，100 帧，单帧 40ms |
| `fgcp_img_02.gif` | 170×300 | 1.14 MB | **GIF 动图**，100 帧，单帧 40ms |
| `fgcp_bg.webp` | — | 29 KB | 皮肤主背景 |
| `fgcp_img_01.png` / `_02.png` | — | 5.7 KB / 5.0 KB | 前景图 |
| `fgcp_img_bg_01~05.png` / `_061.png` | — | 5~36 KB ×6 | **底层装饰图（6 张）** |

四个 GIF 合计约 **5.5 MB**，且**全部是 25 fps 持续循环**（`50 帧 × 40ms = 2000ms`、
`100 帧 × 40ms = 4000ms` 的整数循环）—— 这是**每帧都在产生新内容**的典型负载。

再看它的样式定义（`mainpage.<hash>.css`，明文可读）：

```css
/* 底层装饰：6 张 PNG，全部持续旋转 */
.AeeCui .Dream_box .column .img_bg { position:absolute;
  animation: rotation-… 4s linear infinite }        /* ← 无限旋转 */
.AeeCui .Dream_box .column .img_bg1 { top:-11px; left:27px }
… img_bg2 ~ img_bg6 各自的定位 …
@keyframes rotation-… { 0%{transform:rotate(0deg)} to{transform:rotate(1turn)} }
```

**两条证据对上了**：

- CSS 里的 `.img_bg1 ~ .img_bg6`（6 个）恰好**一一对应**导出的 6 张
  `fgcp_img_bg_0x.png` —— 这就是**最底层那 6 个持续旋转的装饰图**；
- 导出的 4 个 GIF 是**上层**的动图素材（小人、前景装饰），**走 `<img>`/GIF 播放，
  不是 CSS 动画**。

**这就解释了为什么只冻结 CSS 动画，上层 GIF 还在动**（下一节对照组的机制原因）：
GIF 是浏览器内建的动图解码播放，**不受 `animation:none` 管辖**；而底层旋转装饰是
**纯 CSS 动画**，被这两行 CSS 精准关掉了。

**另注**：4 个 GIF **每一帧都带透明通道**（transparent flag = 1），其中两个
（`fg_img_people_01/02`）还有 **32/41 帧使用 disposal=2（恢复背景）** —— 这是
「每帧要清除上一帧、按 alpha 重新混合」的合成方式，比 disposal=1 的纯覆盖更贵。

#### 4.4.2 与官方皮肤包的横向对比（**同一台机器、同一版本**）

同目录下另外两个**官方皮肤**的包，解出来是这样：

| 皮肤包 | 大小 | 资源数 | 素材类型 |
|---|---|---|---|
| `dial29.gpk`（梦境） | 0.06 MB | **1** | 1 张 WebP **静态图** |
| `dial30.gpk`（洛音） | 0.41 MB | **8** | 8 张 PNG **静态图** |
| **`dial31.gpk`（AeeBiCui 博物馆1）** | **5.42 MB** | **13** | **4 个 GIF 动图（各 50~100 帧 @25fps）+ 1 WebP + 8 PNG** |

**差异是数量级的**：

- 官方皮肤是「**一张底图 + 若干静态图标**」，体积 0.06 / 0.41 MB，**包里一个动图都没有**；
- AeeBiCui 是 **5.42 MB，光 GIF 就占 5.5 MB（94%）**，而且是**四个 25fps 无限循环**的动图。

这与 §4.3 的实测（**换官方皮肤后几乎不再闪黑**）指向同一个方向 ——
关键**不在「第三方皮肤」这个标签**，也**不在「有没有动画」**
（官方皮肤同样有粒子等动态特效），而在于：

> **这个皮肤的最底层，是一整层铺满全屏的持续动态；官方皮肤的最底层不是。**

**官方皮肤也有动态，只是不在最底层。** 这一点很关键 —— 它把问题从
「动态 vs 静态」收窄到「**动态位于哪一层**」。

> **这正是你可以自己复现的验证步骤**：`python tools/gpk_dump.py --find` 列出本机所有皮肤包，
> 再 `--list` 逐个看。**看它的最底层素材是什么、有多大、动没动** ——
> 如果你的皮肤最底层也是全屏动态，那可以往这个方向查。

⇒ **这一段能确定的**：该皮肤最底层 = **6 个无限旋转的 CSS 动画装饰（全屏铺满）**
+ 上层 4 个 25fps GIF。闪黑只出现在「最底层那层全屏动态」上，
而这一层正是被冻结的部分。

> ⚠️ **但这只是「相关」，不是「因果」，更不是原因。** 本文**没有找出确切原因**，
> 也**没有去抓这一层的底层证据**（作者已决定不再继续解析）。
> 下一节记录的是本次测试的实际范围与观察结果。


### 4.5 A/B 测试：只冻结「最底层那层全屏动态」

**做法**：给该皮肤注入两行 CSS，把 CSS 动画与过渡停掉（元素本身不删、仍在合成树里，
只是不再动）：

```css
*{animation:none !important;}*{transition:none !important;}
```

**先说清楚它实际冻到了什么**（这一点很重要，别理解成「全冻了」）：

| 层 | 状态 |
|---|---|
| **最底层全屏动态**（6 个旋转装饰 + 背景动效） | **已冻结** ← 本次实际生效的地方 |
| 上层 GIF 小人 | **仍在动**（GIF 自带解码播放，不受 `animation:none` 管辖） |
| 上层粒子特效等其他动态 | **仍在动** |
| 5 秒轮播 / 数字刷新 | **仍照常** |

也就是说：**只把最底层那层全屏动态停了，上面所有动态组件都还在动。**
（`animation:none` 只覆盖 CSS 动画；GIF / 视频 / canvas 这些自带播放循环的元素不受管辖。）

**这个操作的作用层**（很多人会误以为它动到了推流）：

| 层 | 是否受影响 |
|---|---|
| ① 传感器采样 | 不变 |
| ② **DOM/CSS 层**（本次唯一被作用的层） | **最底层 CSS 动画停掉；上层 GIF 等仍照播** |
| ③ 合成/光栅化（Chromium） | 负载下降（最底层不再每帧重画） |
| ④ 抓帧（`DisplaySendPicture` → UYVY 691200B） | **照旧**，帧率、每帧字节数全不变 |
| ⑤ USB bulk 传输 | **照旧** |
| ⑥ 屏端解码 | 照旧 |

⇒ 一句话：**推流照推，只是最底层那层画面不再变化**。变的只有②③层的负载。
（所以这个测试不会「禁用推流」把现象掩盖掉 —— 它只是把最底层那层渲染压力抽掉。）

**实测结果**：**连续测试 6~7 小时，暂时没再发现闪黑**（此前是每天多次 / 数小时级）。

**★★ 关键观察：上层那些动态组件全程都在动**（它们一个都没被禁）：

| 元素 | 是否仍在动 | 由什么驱动 |
|---|---|---|
| **最底层全屏动态** | **已停** | CSS `animation` ← **本次冻结的地方** |
| 上层 GIF 小人 | **仍在动** | GIF 自带解码播放 ← 不受 `animation:none` 管辖 |
| 上层粒子等动态特效 | **仍在动** | ← 不受管辖 |
| 5 秒轮播 | **仍在跳页** | 计时器 + JS 切页 ← 不受管辖 |
| 数字（内存/显存/电压） | **仍每 3.5s 刷新** | 注入器 `refresh_ms` ← 不受管辖 |

⇒ **「上层那些仍在动的东西都没事，只有被停掉的最底层那层不闪了」** ——
这说明**问题很可能出在「最底层这一层的特殊位置/层级」上，而不是「有没有东西在动」**
（毕竟上层同样在动，却看不出问题）。**但到这一步为止，仍然只是相关，没有原因。**

**⚠️ 观察期的诚实说明**：6~7 小时**不是永久验证**。此前闪黑频率是「数小时级 / 每天多次」，
所以这个结果**算一个正面信号，但远不足以定案** —— 只能说「暂时没发现」。
**作者已决定不再继续花时间解析，本节到此为止。**


### 4.6 几种可能性（**纯推测，未验证 —— 不要当结论引用**）

> ⚠️ **这一节是本文最不可靠的部分。** 下面几条都**没有经过任何验证**，
> 作者**也没有去抓这一层的底层证据**。列在这里只是给后来人一个可打的靶子。
> **作者不想再继续花时间解析这些东西了。本节到此为止。**

现状：**已经定位到「最底层那层全屏动态」这个范围**，但没有回答
「**为什么偏偏是这一层**」。以下是几种**可能**的方向：

**可能性 A —— 抓帧与合成竞争（最直接的一条）**

1. 抓帧模块读的是**渲染管线的最终输出位图**（整帧一次读出，691200 字节）。
2. **最底层那层全屏动态**每一帧都要重新光栅化 / 重新提交合成，
   而它**又铺满整屏** —— 一旦这一层没准备好，**受影响的就是整块画面**。
3. **推测**：当读帧动作与合成提交**竞争**（GPU/CPU 负载尖峰时刻），
   这一帧里该层**可能还没被画出来** ⇒ 那块区域抓到空（黑）。
   这**似乎**能对上「黑的是最底层那片」的空间特征。

**可能性 B —— 合成层本身的特性**

最底层那层通过 CSS 动画（`transform` 等）被提升为**独立合成层**，
每帧由合成器重新提交。会不会是**这一层的提交时机**与抓帧读取发生了某种冲突，
而不是「内容没画完」？**（同样只是猜测）**

**可能性 C —— 素材本身**

该皮肤带**大体积 GIF**（四个 50/100 帧动画，含背景图合计约 5.5MB），
解码卡顿可能在那一帧留下未就绪区域。
（但注意：**这些 GIF 在本次测试里全程都在动，却没看到闪** —— 所以这条可能性较弱。）

**可能性 D —— 轮播 / 切页时重建合成层**

轮播切换瞬间会**重建合成层**，新层在没有内容的瞬间也可能呈现为黑。

> **这几条都说不准哪个对、甚至可能都不对。** 要真正确认，必须往抓帧层挂 hook
> （`DisplaySendPicture`），先回答一个前置问题：
> **黑帧是「抓出来的」还是「渲染出来的」**。
> **本项目没有做这一步，作者也决定不再继续了。**
> 这一节就是本项目在这条线上的终点。
>
> **需要特别说明的一点**：有人可能会问「既然上层也有动态（粒子等）却不闪，
> 那是不是说明跟动态无关？」—— **不能这么推**。
> 上层动态**不铺满全屏、也不构成一整层**，与「最底层那种整层全屏动态」**不是一回事**，
> 不能直接类比。


### 4.7 想在你自己的皮肤上照做？（**可选，不是默认工艺**）

> ⚠️ 本仓库**默认不改任何皮肤的动画** —— 因为每个人的皮肤不同，且这会让该皮肤失去动画。
> 下面只是「如果你想照做」的做法。**先确认你自己闪的是哪一层**（§4.4），再动手。

**做法 A · 临时诊断**：用本仓库的诊断工具 `freeze-anim/freeze_anim.py`（独立于注入器，
不影响任何排版配置），支持 `apply` / `undo` / `status` 三种模式，秒级生效、完全可逆。

**做法 B · 固化到自己的配置**：把上面那两行 CSS 追加到**你自己皮肤**的 `css` 字段里，
交给注入器托管（v21 起支持分皮肤绑定，切到别的皮肤会自动撤销）：

```jsonc
"skins": {
  "你的皮肤id": { "css": "……你的排版……*{animation:none !important;}*{transition:none !important;}" }
}
```

**皮肤不同怎么办**：先跑 `skill/tools/probe_skins.py` 探出本机皮肤的类名与官方编号
（内置的那三个名字是**一台机器上的实测值，不是官方标准**），认不出来的皮肤注入器
一律不动 —— 这是故意的安全行为。

**代价**：该皮肤的动画（旋转装饰、过渡、轮播滑动）会永久静止。
只想定位而不想牺牲动画的话，就停在做法 A，或者做「只禁一半」的二分实验。

## 6. 遇到闪黑怎么办（给用户的排查顺序）

> 顺序按「成本从低到高、排除力从强到弱」排。**关键分水岭是第 4 步** ——
> 它决定你后面该往渲染侧走还是往硬件侧走。
>
> ⚠️ **提醒**：下面第 4 步「冻结后不闪了」只能说明**这一条线值得继续查**，
> **不等于原因已找到**（本文就没找到）。别把「不闪了」当成「问题解决了」。

1. **先看清楚是「哪一层」在闪**（§4.4，零成本、信息量最大）：
   黑掉的是**整屏**，还是**只有某一块**？上方组件（数字/图标）跟着闪了吗？
   - **只有最底层那片全屏区域在闪** → 重点往「**最底层是不是一整层动态**」方向查，跳到第 3 步
   - 整屏一起黑 → 继续第 2 步往下走
   > 注意区分：**「有动态」和「最底层是一整层动态」不是一回事** ——
   > 很多皮肤都有粒子等上层动态特效，但那不构成「铺满全屏的底层动态层」。
2. **定性**：黑屏时内容还在吗？多久恢复？出现 logo / 待机画面吗？（§1 的三层区分）
   —— 若推流日志显示闪黑时刻推流**完全正常**，硬件/驱动/推流线程即可排除（§4.2 的取证法）
3. **★ 解包看你的皮肤最底层是什么**（§4.4.1，纯只读、可复现，不用装任何东西）：
   `python tools/gpk_dump.py --find` 找到皮肤包，再 `--list` 看你那个皮肤的清单：
   - **最底层不是整层动态** → 与本文现象不同，闪黑要往别处查（去第 5 步）
   - **最底层是一整层全屏动态** → **可以一试**第 4 步的 A/B 测试（注意：这是「值得查」，
     不是「已确认因果」）
4. **★ 只冻结最底层动态做 A/B**（§4.5）—— 把 CSS 动画停掉，观察闪黑是否消失：
   - **不闪了** → 这条线**值得继续查**（但原因仍未明，见 §4.6），可按 §4.7 处置
   - **仍闪** → 与页面动画无关，回到「软件自身 / 屏 / 硬件」方向（继续第 5 步）
   > 做这一步时**顺便记下上层哪些还在动**（GIF？粒子？轮播？数字？）—— 它们会告诉你
   > 「不是所有动态都有问题」，帮你把范围收到「最底层那一层」上，**避免过度归因**。
5. **换官方皮肤对照**（§4.3）—— 排除/确认第三方皮肤这个变量
6. **干净重装 Myth.Cool**（§4.1）—— 成本低、实测**缓解但不根治**，顺手排掉灰度版本混用
7. **退出主板厂商灯控/监控套件对照**（MSI Center / 奥创等）—— 通用冲突模式
8. 仍闪 → 查屏的生产日期（背面标签 / 报 SN 给客服），参考网上「换屏解决」先例找售后

> 关于第 1、3 步的顺序：作者本人是先靠「**看**出来只有底层动态在闪」（第 1 步）
> 才找到方向的 —— 而在那之前，已经在「注入器 ↔ 软件 ↔ 硬件」之间绕了很久。
> 第 3 步（解包）是后来补上的**更硬的一条**：它把「我觉得它在动」变成
> 「**它确实是 4 个 25fps 的 GIF + 6 个无限旋转**」这种可量化的事实，
> 而且**不用真的改动系统**，任何人都能在自己机器上跑一遍。
> **但请注意**：这条事实**只说明「它在动」，不说明「动就会闪」** ——
> 为什么动会闪，本文没有答案。
>
> 另建议顺手做一次**「停用注入器 10 分钟」对照**（删计划任务，或
> `schtasks /Change /TN <任务名> /DISABLE`，对照完 `/ENABLE`）—— 成本极低，
> 能把「是不是注入器干的」这个最容易被自己怀疑的变量彻底摘掉。
