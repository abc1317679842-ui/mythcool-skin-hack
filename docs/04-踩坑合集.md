# 04 · 踩坑合集 ★

> 这一篇是本项目最有价值的部分。下面每一条都是**真踩过、真浪费时间**的坑，
> 按「症状 → 原因 → 正确做法」写。改 Myth.Cool 皮肤（或做同类 Electron 注入）之前先读一遍，
> 能省几个小时。

---

## 1. `webapp.gpk` 有完整性校验，不能改文件

**症状**：改了皮肤文件，整个皮肤失效 / 软件报错。

**原因**：`gpk` 是带校验的 asar 式归档。

**正确做法**：只在**运行时改内存**。所有改动都在渲染进程的 DOM 和主进程的 JS 里，
软件重启就干净 —— 这也是本项目「完全可逆」的来源。

---

## 2. ★★ 类名会被多个组件复用 —— 用宽选择器会误伤一大片

**症状**：修好了 A 组件，B 组件却坏了（一个消失、一个位移）。

**原因**：Myth.Cool 的类名很多来自**配置数据**，不是写死的字面量：

```js
// mainpage.js 里不同组件用的是同一个 customClass
networkMonitoringVesselsData:  { num:1, unit:"MB/s", customClass:"AeeAndCui" }
CPUmonitoringVesselsData:      { num:1, unit:"℃",    customClass:"AeeAndCui img_back" }
GPUmonitoringVesselsData:      { num:1, unit:"W",     customClass:"AeeAndCui img_back" }
```

它们走同一个渲染分支 `1===e.num → div.hardware-infor.outside.[customClass]`，
所以 `.hardware-infor.outside.AeeAndCui{...}` 这一条规则**同时命中好几个组件**。

**后果实测**（用当时那条宽规则）：

| 规则 | 后果 |
|---|---|
| `:not(.triangle_icon2){left:auto;right:-11px}` | 把右侧 4 个标签从 `left:10px` 硬拽成右对齐 → **其中一个直接出界** |
| `width:auto;min-width:0` | 宽度从 `BoxWidth:134` 收缩 → 自带的 `background` 图片被裁 → **右边框整段消失** |

**正确做法**：

1. **改任何选择器之前，先在页面里确认它匹配几个元素**：
   `document.querySelectorAll('你的选择器').length`
2. **优先用「运行时内容特征」定位**，而不是类名：

```js
// 只认「块里的 span 文本是 MB/s」的那种块 —— 这才是网络块
var els = document.querySelectorAll('.hardware-infor.outside.AeeAndCui');
for (var i = 0; i < els.length; i++) {
  var sp = els[i].querySelector('span');
  if (String(sp.textContent || '').trim() !== 'MB/s') continue;   // ← 只碰网络块
  els[i].style.setProperty('clip-path', 'none', 'important');     // inline !important 必胜
}
```

3. 实在要用类名，就用**独有的那个类**做 `:not()` 排除，例如 `:not(.img_back)`。

## 3. ★★ `clip-path` 是隐形裁切源，`scrollWidth` 查不出来

**症状**：文字最右边总是被切掉一点（本例是 `MB/s` 末尾的 `s`）。
把元素的 `overflow`、`padding` 全查了一遍，**全都正常**。

**原因**：皮肤 CSS 里有这么一条：

```css
.hardware-infor[data-v-b5fe9c4a]{
  -webkit-clip-path: polygon(0 0, 9% 100%, 100% 100%, 91% 0);
  background: linear-gradient(90deg, #a196f3, rgba(161,150,243,0));
}
```

**那个 9% 斜角本来是切它自己的紫色渐变底的。** 但本皮肤把 `background` 改成了
`transparent` 却没撤斜角 —— 于是斜角只剩一个作用：**把最右 9% 的文字斜着削掉**。

而且**百分比随元素尺寸走**：数字越长块越宽 ⇒ 斜切区绝对量越大 ⇒ 削得越多
（用户的原话是「S 显示得越来越少」，当时还以为是"自适应在跳动"）。

**为什么之前找了两轮都没找到**：`clip-path` **完全不改变布局尺寸** ——
`scrollWidth == clientWidth` 恒成立，查 `overflow` 永远查不到它。

**正确做法**：判断「元素被裁」的完整清单是

```
overflow（含所有祖先）
  → clip-path / -webkit-clip-path     ← 最容易漏
  → mask / -webkit-mask
  → contain: paint
```

治本：`clip-path: none !important`。别指望调字号或 padding ——
padding 的百分比是相对包含块算的，治不了。

**另一个更可靠的判别手段**：用 `document.elementsFromPoint()` **沿元素长轴逐像素采样**，
看最后一个是哪个 px 还能命中原元素 —— 被裁掉的部分不参与命中测试，
所以能**精确量出可见末端**，不靠目测也不靠推算。

## 4. `scrollWidth == clientWidth` 证明不了「没被裁」

**症状**：拿到 `scrollW == clientW` 的数据，据此判定「没被裁」，结论错了。

**原因**：被检查的元素自己 `overflow: visible`，**它本来就不会裁自己**。
裁切可以发生在**任意祖先** —— 而当时的 dump 里只取了「往上第一个 position != static」
的祖先，**没有任何一层祖先的 overflow 被 dump**。

**正确做法**：dump **完整祖先链**，每一层都记 `overflow` / `clip-path` / 真实
padding-box 边界。本项目就是在补上祖先链之后一眼看到 `clip-path` 的
（当初只 dump `overflow` 的话，永远找不到）。

## 5. ★ Electron 子进程的启动时间完全相同 —— 不能按时间选主进程

**症状**：脚本 attach 上的进程里没有 `require`，注入全失败。

**原因**：MythCool.exe 有 5 个进程，**主进程和 4 个 helper 的启动时间一模一样**：

```
pid=26308 ppid=22692 created=05:37:02   ← 主进程
pid=16708 ppid=26308 created=05:37:02   ← --type=gpu-process
pid=27868 ppid=26308 created=05:37:02
pid=11992 ppid=26308 created=05:37:02
pid=23164 ppid=26308 created=05:37:09
```

`Get-Process | Sort-Object StartTime | Select -First 1` **选不准**。

而且注意：**这里有两道墙，不是一道**：

1. **权限墙**：Myth.Cool 主进程是高完整性（提权）进程。非提权时 frida
   **枚举都枚举不到它**（只暴露 gpu-process），就算你用 WMI 拿到了正确 PID，
   `attach` 也会因为打不开进程句柄而失败。所以**注入器必须与主进程同级权限**
   —— 这就是本仓库要求管理员安装、计划任务用 `RunLevel Highest` 的原因。
2. **选择墙**：即使已提权，5 个进程 StartTime 全相同，还必须用下面的
   父子关系判据选出主进程，否则 attach 到 gpu-process 会报
   `ProcessNotRespondingError`。

> ⚠️ 我们在这两道墙上各犯过一次错：先是 attach 到 gpu-process 报
> `ProcessNotRespondingError`（这是「选择墙」）；后来又在提权环境里用父子判据
> 成功后，**错误地把成功全归因于「选对进程」，一度总结成「非提权也能注入」**。
> 实测打脸（2026-09-28）：非提权会话下 WMI 能看到全部 6 个进程和 PPID，
> 但 frida 只暴露 1 个（gpu-process），主进程完全不可见。
> **结论：PPID 判据不需要特权（WMI 免特权），但 attach 本身必须要特权。**
> 两句话都是实测，别只记一半。

**正确做法**：用**父子关系**判据选主进程（`ParentProcessId` 不需要特权就能读），
同时整个注入链路（安装、计划任务）以管理员运行：

```powershell
$ids  = @($raw | ForEach-Object { $_.ProcessId })
$cand = @($raw | Where-Object { $ids -notcontains $_.ParentProcessId })
# 主进程 = 唯一一个「父进程不是 MythCool.exe」的
```

## 6. `-WindowStyle Hidden` 治不了闪窗

**症状**：计划任务每分钟跑一次，屏幕上**有个黑框一闪而过**。

**原因**：`powershell.exe` 是**控制台子系统**程序。Windows 在**进程创建的那一刻**
就给它分配了 conhost 窗口，而 `-WindowStyle Hidden` 是 PowerShell **启动之后**
才执行的 —— 中间那几百毫秒窗口就是可见的。

**正确做法**：用 **`wscript.exe`** 启动（GUI 子系统，**根本没有控制台**），
再用 VBS 的 `Run(cmd, 0, True)` 隐藏子进程：

```vbs
rc = sh.Run("powershell.exe -NoProfile ... -File ""...\Inject.ps1""", 0, True)
'                                                                  ↑  ↑
'                                                  0 = 隐藏窗口     等待完成
```

**为什么第二个参数必须是 `True`**：不等待的话任务会立即结束，
`MultipleInstances=IgnoreNew` 和 `ExecutionTimeLimit` 就都失效了。

## 7. `*> 文件` 重定向失败会中止整轮

**症状**：注入莫名其妙没执行，日志里只有一句「injector threw」。

**原因**：PowerShell 里 `& $exe ... *> $file` 如果**打不开目标文件**（被占用、无权限），
会产生 **terminating error** —— `try/catch` 也接不住重定向本身的失败，整轮直接中断。

**正确做法**：用管道，不要用文件重定向：

```powershell
& $PY $MAIN $cur 2>&1 | Out-Null      # 管道不打开文件句柄，失败也不会中断
```

（输出记录交给被调脚本自己写日志文件。）

## 8. 跨窗口的 `localStorage` 写入抓不到

**症状**：hooks 了 `Storage.prototype.setItem`，但一次都没触发，看起来像"数据没更新"。

**原因**：`bg_sensor_data` 是 **background 窗口**写的，
而你在 **mainpage 窗口**里 hook 的是**本窗口**的 `Storage.prototype` ——
**跨窗口写入永远抓不到**。

**正确做法**：用跨窗口事件：

```js
window.addEventListener('storage', function (e) {
  if (e.key === 'bg_sensor_data') { /* 这里才会触发 */ }
});
```

## 9. CSS 属性字符串匹配陷阱：`[style*="clip-path"]` 在 `clip-path: none` 时仍然匹配

**症状**：MutationObserver 的条件恒为假，观察器**从来没触发过**。

**原因**：本来想表达"如果还没有我们处理过的块"，写成了：

```js
!document.querySelector('.hardware-infor[style*="clip-path"]')
```

但处理完之后元素的行内样式是 `clip-path: none` —— **字符串里仍然含 "clip-path"**，
所以选择器**照样匹配** ⇒ `!matches` 恒为 `false` ⇒ 条件永远不成立。

**正确做法**：别用属性字符串匹配来表达"处理过了"，
改用**语义明确的检查**（比如"目标元素是否还在"），或者干脆打标记：
`el.setAttribute('data-patched', '1')` 然后查 `[data-patched]`。

## 10. Vue 组件重建后钩子失效 —— 守卫要**版本化**命名

**症状**：新版本脚本装上了，但 `$watch` 就是不生效。

**原因**：旧版本在 `vm` 上留了个 `vm.__mtc_hooked = true` 的标记，
新版本第一句是 `if (vm.__mtc_hooked) return true;` ⇒ **新版的钩子从来没注册进去**。

**正确做法**：每个版本用**自己的**守卫名：

```js
function hookUpdates() {
  var vm = findVmOnce('gpumemload');
  vm.__mtc_hooked = true;        // 占住旧版本的标记，别让旧版再重复 hook
  if (vm.__mtc_v13hooked) return true;
  vm.$watch('gpumemload', ...);
  vm.__mtc_v13hooked = true;     // ← 自己的守卫，独立命名
}
```

另外 `findVmOnce` 要**允许重新查找** —— Vue 实例销毁重建后缓存的 vm 就失效了：

```js
if (vmCache && vmCache.$data && !vmCache._isDestroyed
    && vmCache.$el && document.contains(vmCache.$el)) return vmCache;
vmCache = null;   // 失效就重新找
```

## 11. 写 JSON 字符串字段后**必须** `json.load()` 验证

**症状**：热调通道推送后**没有任何反应**，也不报错。

**原因**：在 JSON 的说明字段里写了裸双引号（`customClass = "AeeAndCui img_back"`），
直接把 JSON 结构破坏了。而热通道那边的 `JSON.parse` 失败是**静默跳过**的：

```js
try { JSON.parse(t); } catch (e) { return; }   // ← 不写 ack、不报错、什么都不做
```

**正确做法**：写完 JSON 一定要验一次：

```python
import json
json.load(open('tune.json', encoding='utf-8'))   # 抛异常就是坏了
```

**另外一个推论**：凡是"推送了但没反应"的情况，**先验 JSON，再怀疑别的**。

## 12. ★ 诊断脚本里塞写操作 = 违约

**症状**：本来只是想"看一眼"，结果把界面搞崩了。

**原因**：一个诊断脚本把「探测」和「修复试探」写在一起 —— 修复逻辑本身有
bug（对 `rotate(90deg)` 下的边界计算用了错误的轴），把 `BODY` 的 `overflow`
改成了 `visible` ⇒ **视口出滚动条 + 绝对定位基准变化 ⇒ 所有组件漂移**，
而且 renderer 当场卡死，连回滚脚本都注入不进去。

**正确做法**：

- **诊断永远纯读**：只 dump 数据、只测量、不写任何东西
- **写操作单独一轮、单独确认**
- 一次只改一个变量，改完立刻验证

**以及一条补充**：**renderer 一旦 hang，任何注入类的补救都是空的** ——
`executeJavaScript` 永不 resolve，什么都进不去。**直接重启软件**才是唯一解
（好在所有改动都在内存里，重启即净）。

## 13. 数据会变长的元素：定位要固定「变化的那一侧」

**症状**：对齐做好的两块，用着用着就错位了 —— 数字越长偏得越多。

**原因**：一块是 `left` 固定（左边缘对齐），一块是 `right` 固定（右边缘对齐）。
`left` 固定的那块，数字变长时内容**向右长** ⇒ 它的**右边缘**（也就是用来对齐别人的那一侧）
一直在飘。

**正确做法**：**看哪一侧需要对齐，就固定哪一侧**：

- 右边缘要对齐别人 → 固定 `right`，让它只往左长
- 左边缘要对齐 → 固定 `left`

本项目就是这么解决的（`left:auto; right:-11px`），改完对齐与数据长度**永久无关**。

---

## 14. `width: auto` 优于「加宽到某个固定值」

**症状**：皮肤写死了 `width:134px`，内容一长就被 `flex-shrink` 压扁、文字被裁。

**原因**：块是 flex 容器，宽度固定且内容溢出时，子元素会被压缩。

**正确做法**：

```css
.target{ width:auto !important; min-width:0 !important; }
.target *{ white-space:nowrap !important; flex-shrink:0 !important; }
```

**`width:auto` + `flex-shrink:0`** 是治「皮肤写死尺寸把内容挤掉」的通用拳 ——
换字号、换内容长度都不用重新算数值。

## 15. 改完不知道生效没有？先看这几个信号

排查顺序（从便宜到贵）：

1. **热通道回执文件**的**时间戳** —— 有没有推送成功
2. **产物里有没有该功能留下的专属字段** —— 比看文件修改时间可靠得多
3. `document.querySelectorAll('你的选择器').length` —— 元素在不在
4. 最终**只能靠人眼**看副屏（USB 直驱屏是抓不到屏的：`GetSystemMetrics(80)=1`，
   它不算 Windows 显示器）

> 本项目注入器会 `webContents.capturePage()` 自拍一张图落盘 —— 这是**唯一的**看图方式。

## 16. 别急着动手 —— 先确认「要改的东西到底在哪」

**症状**：想改皮肤样式，第一反应是去软件安装目录 / AppData 找皮肤文件。

**弯路实测**：`AppData\Local\MythCool` 下 **148 个文件**逐个排查、全盘按皮肤名
字符串搜索 —— 最后才发现皮肤**不是独立包**，整套 UI 打包在
`webapp.gpk` 一个归档里。

**正确做法**：对不熟悉的目标软件，先花 10 分钟做「资产定位」：
1. 安装目录、AppData（Local/Roaming）两处列全量文件
2. 全盘按皮肤独特字符串（这里是一句 UI 文案）搜一遍
3. 确认了唯一目标（gpk）再研究它的格式 —— 而不是在错误的目录里调 CSS

## 17. gpk 归档可以「当目录读」（技巧条）

`gpk` 是 asar 式归档，Node 的 `fs.readFileSync('xxx.gpk/windows/pages/mainpage.html')`
**可以直接当路径读**（Electron 打包层透传）—— 不用先解包整个文件。
这是后续所有源码分析（渲染分支、CSS 规则、数据链路）的基础。

---

## 18. V8 C++ 注入链的四个坑

用 Frida 走 `Isolate::GetCurrent → GetCurrentContext → HandleScope →
String::NewFromUtf8 → Script::Compile → Script::Run` 这条链时：

1. **符号是 C++ mangled name**（如 `?GetCurrent@Isolate@v8@@SAPAV12@XZ`），
   不是普通导出名。Electron 大版本升级后 mangled name 可能变化 ——
   代码里对每个符号做「取不到就跳过」的兜底，别写死依赖。
2. **`Isolate::GetCurrent` 必须在 JS 线程上调用**。Frida 的 script 默认跑在
   自己的线程上，直接调会拿到 null —— 必须先 hook 一个 libuv 入口
   （`uv_timer_start` / `uv_async_send`），借 Node 的回调线程执行注入。
3. **HandleScope 必须先建**（`??0HandleScope@v8@@QAE@PAVIsolate@1@@Z`），
   否则局部句柄落在空 scope 上，行为未定义。
4. `NewFromUtf8` 的字符长度按**字节**传，源码字符串先在宿主侧拼好再整体送入，
   不要在 C++ 层分段拼。

---

## 19. 运行期注入不需要「抢时机」

hook `uv_timer_start` 是为了在**进程初始化早期**抢注入时机；但 Electron 主进程
运行期 `uv_async_send` **高频触发**（传感器数据每次更新都会调）—— 对已运行的
进程直接 hook `uv_async_send`，几秒内就能进 Node 线程，不用任何时机技巧。
只有「进程刚启动就要注入」的场景才需要两个 hook 都挂。

## 20. ★ 对非主进程的 attach 尝试，会让 Electron 画面闪黑

**症状**：探测脚本按「PID 从小到大」逐个 attach，对 gpu/renderer 进程的
`ProcessNotRespondingError` attach 失败期间，**副屏肉眼可见地闪黑一下**
（没完全黑下去就恢复）。实测一次连试 4 个错误进程 = 连续几次闪黑。

**原因**：Frida 对每个 attach 目标都会尝试注入 frida-agent（加载 DLL、
创建线程），失败后回滚 —— 这个加载/回滚过程会扰动目标进程的渲染管线
（gpu-process / renderer 正在参与副屏合成）。

**正确做法**：
- **永远不要「逐个试」**。用父子关系判据（见 #5）或 WMI 查 PPID 一次锁定主进程，
  只 attach 这一个。
- 探测类脚本宁可多花一步查准，也不要对 Electron 的任何子进程练手。

## 21. Windows PID 回绕：「主进程 PID 最小」不可靠

**症状**：脚本假设「主进程比子进程先启动，所以 PID 最小」，按 PID 排序取第一个。
开机后一段时间内确实成立；**重启电脑后 PID 计数回绕**，主进程 PID 可能排在
候选第 5 位 —— 前 4 个全是 helper，逐个 attach 全失败（还触发 #20 的闪黑）。

**正确做法**：唯一可靠的主进程判据是 **PPID 规则**（父进程不在 MythCool 集合里），
WMI 查 `ProcessId/ParentProcessId` 无需特权。启动时间、PID 大小都不要用。

## 22. 注入器的「参数回读」是推送前的快照 —— 别拿它判断页面最终状态

**症状**：注入完成后回读页面参数，显示 `cssLen:0`、字号/坐标全是另一套 ——
误以为 tune.json 被人改过，排查了半天「谁改的」。

**原因**：自检 JSON 是 `executeJavaScript(PATCH)` 的返回值，产生于
**initial tune push 之前** —— 它反映的是 v13 内置默认参数，不是推送后的最终状态。
而 initial push 是异步的，推完后没有再写一次回读。

**正确做法**：判断页面真实生效的参数，看两个地方：
1. **热通道 ack 文件**（推送成功就有时间戳 + 字节数）
2. 推送完成后的**第二次回读**（注入器应在 push 完成后 append 一次，而不是只留
   push 前的快照）

> 附：`pushed N bytes` 的 N 是 **JS 字符串长度（字符数）**，不是 UTF-8 文件字节数 ——
> 含中文的 tune.json 两者对不上（4632 字节的文件报 3434），是正常的。

## 23. 发布到 GitHub 的四个小坑

1. **LICENSE 文件必须是纯许可证正文**。混入任何说明文字（商标声明、使用范围等）
   GitHub 就识别成 `NOASSERTION` —— 把说明拆到单独的 `NOTICE.md`，识别恢复 MIT。
2. **topics 只收小写字母/数字/连字符** —— 中文关键词物理上塞不进去。中文可搜索面 =
   仓库 description（展示会截断，关键词放最前）+ README 全文。
3. **本机有 git push 拦截策略时**，走 GitHub REST API 全流程（建仓 → blobs →
   trees → commit → 更新 ref）完全等价，且可编程核验。
4. **python urllib 在有系统代理的环境里会被代理层挡**，用 curl 发请求更稳。
   单文件更新流程：`GET ref → GET commit → POST blob(base64) → POST tree(base_tree)
   → POST commit → PATCH ref`，最后拉远端文件做逐字节比对。

# 补充篇 · v20~v22 的坑（2026-09-30）

> 这一批全是「注入器本身看起来没问题、但改完之后**静默不生效**」类的坑。
> 共同特征：**每一个都能骗过日志**，只有拿活体数据对比才看得出来。

## 24. ★★★ 切换皮肤会重建渲染进程 —— 注入的东西会整体蒸发

**现象**：第一次切回目标皮肤有效，**多次切换（尤其切到自定义皮肤）之后就再也不注入了**。

**真因**：切皮肤会**销毁并重建 mainpage 渲染进程**。页面里注入的一切 ——
`<style>`、浮层 DOM、`setInterval`、`MutationObserver`、换肤探测 —— **全部随之消失**。
而幂等判据只看「官方软件有没有重启」（PID），**页面重建不改 PID** ⇒ 页面一重建就永远不再注入。

**实测铁证**（切回 AeeBiCui 后探针）：

```js
document.querySelector('.mainpage_jx').children[0].className   // "AeeCui"  ← 皮肤识别是对的
typeof window.__mtc_apply                                      // "undefined" ← 代码整个没了
!!window.__mtc_skinTimer                                       // false
```

**修**：**守卫必须有一份跑在主进程**（它活得过页面重建），两层：
① `app.on('web-contents-created')` → `wc.on('did-finish-load')` 事件驱动；
② 每 10 s 查一次 `typeof window.__mtc_apply` 兜底。发现是 `undefined` 就重打 PATCH，
并**立刻补推一次 `tune.json`**（不等下一次热调）。

**另一条隐蔽的复活通路**：升级注入器后，**上一版本的闭包仍驻留在页面里**。它有 3 条复活通路：

| 通路 | 能清吗 |
|---|---|
| `window.__mtc_v13timer`（`setInterval`） | ✅ `clearInterval` |
| `window.__mtc_mo`（`MutationObserver`） | ✅ `disconnect()` |
| **Vue `$watch('gpumemload' / 'memoryloads')`** | ❌ **没保存 unwatch 函数，清不掉** |

第三条是活的：**传感器值一变就把刚删掉的浮层原地重建**。所以「撤销」必须额外做
`killLegacyWatchers()`：遍历 `vm._watchers`，**只拆 `w.user === true` 且 `expOrFn` 恰好是那两个字段的**
（`user === true` 才排除 Vue 自己的 render watcher），并在 `refresh()` 开头加一道
`if (SKIN_SKIP) return;` 拦漏网之鱼。

## 25. ★★ 幂等判据只看 PID ⇒ 改了注入器代码永远不生效

**现象**：替换了 `inject_main.py`，计划任务每分钟都在跑、`LastTaskResult = 0`，
但 **`inject.log` 一行都不增加**，`state` 里也什么都没变。

**真因**：**有两处独立的「PID 没变就跳过」**，而且第一处是拦门的那个：

1. `InjectSilent.vbs`（**计划任务的真正入口**，动作是 `wscript.exe //B //NoLogo ...InjectSilent.vbs`）
   里面自己写了一套 `If pid <> "" And pid = last Then WScript.Quit 0` ⇒ **`Inject.ps1` 连启动的机会都没有**；
2. 即使进了 `Inject.ps1`，它也只看 PID。

替换代码**不改 PID**，所以两处都跳 ⇒ 新代码永远进不了页面。

**修**：
- **删掉 VBS 里的 PID 跳过**（只留「Myth.Cool 没在跑且 state=NONE」）—— 正确性 > 省下的 ~250 ms；
- `Inject.ps1` 的幂等键加 `inject_main.py` 的 **sha256**（写 `state\last_hash.txt`）。

> ⚠️ **绝不要用 mtime 当判据**：`Copy-Item` 会把**源文件的时间戳**带给目标，
> 「目标比上次新」这个判断会说谎（#6 同源）。哈希不会。

**教训**：改部署链路前，先确认**真正的入口是哪个文件** —— 这里入口是 VBS，不是 ps1。

## 26. ★★ Python 路径写死 ⇒ 换装机布局直接 FATAL

**现象**：上面那个修完，ps1 能进了，结果报 `FATAL missing python` + `exit 3`，**注入彻底死掉**。

**真因**：`Inject.ps1` 里写死 `venv\Scripts\python.exe`，但本机**根本没有 `venv` 目录** ——
实际运行时在 `python\python.exe`。`Setup-Runtime.ps1` 能建 venv 时会生成前者，
在**没有基础 Python 的机器**上会退回嵌入式运行时（后者）。

**修**：运行时按顺序探测 `venv\Scripts\python.exe` → `python\python.exe` →
`python\Scripts\python.exe` → PATH 上的 `python.exe`；都没有才 FATAL，
并把**试过的全部路径**打进日志。

**教训**：仓库里的路径常量要按「装机可能有多种布局」写，别只认自己那台。

## 27. ★ 注入器返回的「参数回读」是**推送前**的快照 —— 新页面上尤其会骗人

**现象**：日志显示 `配置段=None / 绑定模式=False / cssLen=0`，
看着像「皮肤没认出来、配置没生效」，**但界面其实是好的**。

**真因**：MAIN 的顺序是「先 `executeJavaScript(PATCHCODE)`，再 `arm()` → `pushTune()`」。
PATCH 先落地时，它跑 `applyAll()` 的那一刻 `window.__MTC_TUNE` 还没送到 ⇒
**返回的 `RES` 是出厂默认值**。界面随后被 `pushTune` 里那次 `__mtc_apply` 改对了，
但**这份快照是旧的**。

修之前之所以不常暴露：旧页面上 `window.__MTC_TUNE` 可能还残留着上一次注入的值。

**修**：PATCH 末尾若 `__MTC_TUNE` 还没到就等（≤2.5 s，返回 Promise）；到之后若发现
`RES.cfg.tuneSrc` 仍是 false，补跑一次 `applyAll()` 再返回。

**教训**：这和第 22 条是同一个病根 —— **「注入器自己报的状态」和「页面最终状态」是两回事**。
判断最终状态要看 `RES.skin` / `RES.items` / 真去 DOM 里量。

## 28. ★ 皮肤判据的两个陷阱：`.Dream_box` 和 `.dial29`

做「跟随皮肤」时要认出当前是哪套皮肤。**主判据 = `.mainpage_jx` 的第一个元素子节点的 class**
（那就是 Vue 皮肤组件的挂载点）。两个看似可行、**实际会误判**的候选：

| 候选 | 为什么不能用 |
|---|---|
| `.Dream_box` | **公共子组件** —— 真机实测：**梦境皮肤下也命中 1 个**，AeeBiCui 里也有 |
| `.dial29` | 源码里 `dial31` 在**非 960 高度**时会被包一层 `<div class="dial29">` ⇒ **类名 ≠ 皮肤** |

**自定义皮肤**是独立窗口（`diySkin.html`），副屏主页面根本不加载 ⇒ 注入器压根不会运行；
万一将来搬进主页面，识别结果是 `unknown` → 不在白名单 → **不动界面**（双保险）。

## 29. `ProgramData\MythCoolInject\` 的 ACL：能新建、**不能覆盖、也不能删除**

实测：往该目录**新建**文件 OK；但覆盖已存在的文件、删除任何文件（**包括自己刚建的那个**）
一律 `Permission denied`。

**后果**：在那儿造的**临时/测试文件会永久留下**（实测留了 `_wtest.tmp` 69KB + `log\_wtest.log`，
得请用户开管理员终端清）。

**规矩**：要临时文件就去工作区或 `D:\测试临时文件夹\`，**别碰 ProgramData**。

## 30. 「任务跑了但没日志」还有第三层：非提权写日志被静默吞

非提权终端跑 `Inject.ps1` 时，`Add-Content` 写 `log\inject.log` 会抛
`UnauthorizedAccessException`，而 `Log()` 外面包了 `try/catch` ⇒ **什么痕迹都不留**。

排查「任务在跑但日志不增长」时按顺序排除：
① 先看 `Get-ScheduledTaskInfo` 的 `LastRunTime`（**任务每分钟才一次，别拿刚读的日志当定论**）；
② 是不是被幂等跳过了（PID + 哈希都没变）；
③ 是不是被 VBS 的快速跳过拦了；
④ 是不是 `Log()` 写不进去被吞了。
